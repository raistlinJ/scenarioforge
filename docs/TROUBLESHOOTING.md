# Troubleshooting

- **`core-python` not found`** – set `WEBUI_PY` before `make host-web` or rely on `python3`; the backend falls back to `sys.executable` if needed.
- **`Attack graph PDF unavailable (Graphviz not installed)`** – install Graphviz so the `dot` executable is on `PATH`. On macOS run `brew install graphviz`; on Debian/Ubuntu run `sudo apt-get install graphviz`. Docker Compose runs include Graphviz after rebuilding the web image.
- **Empty TLS cert folder (`nginx/certs`)** – run `scripts/dev_gen_certs.sh` or `make dev-certs` before composing nginx.
- **`core-daemon` unreachable`** – verify daemon status and host/port; GUI run modal will surface connection issues immediately.
- **Docker vulnerabilities skipped** – ensure images are downloaded/pulled via the Vulnerabilities catalog and Docker is available to the host.
- **Log dock won’t auto-scroll** – click the “Follow Off/On” toggle to re-enable auto-follow.
- **Proxmox validate returns 502 (nginx)** – the expected backend route is `POST /api/proxmox/validate`. A JSON validation/authentication error means the request reached Flask; a 502 usually points to the nginx container not reaching the Web UI backend, so check `docker compose ps`, `docker compose logs web nginx`, and `/healthz`.
- **Runtime validation reports issues** – inspect the run's `validation_summary` from `GET /run_status/<run_id>` while the run is retained in memory, or use the Markdown/JSON report artifacts under `./reports/`. Strict success requires `validation_summary.ok == true` and zero issue counters such as `missing_nodes`, `docker_not_running`, `injects_missing`, `generator_outputs_missing`, and `generator_injects_missing`.
- **`Cannot reach the CORE VM over SSH at <host>:<port>`** – the SSH endpoint is TCP-probed before anything else, so this fails in about three seconds and names the endpoint actually dialled. The VM may be powered off, or on a network this machine cannot currently reach. In VM mode the endpoint comes from `CORE_SSH_HOST`/`CORE_SSH_PORT` in `.scenarioforge.env` and **not** from the scenario XML; see [Runtime Metadata And Ground Truth](reference/SCENARIO_XML_SCHEMA.md#coreconnection).
- **`Docker node(s) not running: …` followed by a compose error** – the reason from `docker compose up` is appended to the message and logged in full. `open /home/<user>/.docker/buildx/.lock: permission denied` means a docker command was once run as root and left root-owned state in that user's config directory; execute repairs this automatically unless `CORETG_REPAIR_DOCKER_HOME_PERMS=0`.
- **`Conflict. The container name "/docker-N" is already in use`** – a container from an earlier run still holds the name. Execute clears these before building the topology; set `CORETG_SKIP_STALE_DOCKER_CLEANUP=1` only if you need to keep them, and expect this error if you do.
- **`CORE session stayed in "configuration": it never instantiated the topology`** – the containers are running but CORE never wired them, so no node has an interface or address and the scenario is not deployed. Check the core-daemon journal (`journalctl -u core-daemon`) for a `thread pool exception` naming the node that failed; CORE swallows per-node startup errors, so its log is usually the only place the real cause appears.
- **A generator fix appears to have no effect** – artifacts are regenerated when they are missing *or* when the generator's source is newer than what it produced. If a stale output survives anyway, delete its directory under `/tmp/vulns/flag_node_generators_runs/<scenario>/` and re-run. Note that CORE builds a per-session image and reuses it while the tag exists, so a stale `core-<session>-<node>-*` image can also pin old code; execute deletes every such image before building the topology so each node rebuilds from its current context.
- **A node runs the wrong generator's code** – CORE tags what it builds `core-<session>-<node>-<name>-<service>`, and session and node ids repeat between runs, so the tag carries no content identity and `docker compose up -d` builds only when the tag is absent. One observed run rebuilt a node from a Python context but started a twelve-hour-old WebDAV image, which crash-looped on `DAV_USER: parameter not set`. Execute now clears these images up front; if you hit it on an older build, `docker image rm core-<session>-<node>-<name>-<service>`.
- **`cannot join network namespace of container: … is restarting`** – the helper that copies injects joins the node's network namespace, and the node is in a restart loop, so that namespace never settles. The helper is the symptom; look at the node with `docker logs <node>` and `docker inspect <node> --format '{{.State.ExitCode}} {{.RestartCount}}'`. A non-zero exit repeated a few times means the application inside is failing, not the namespace wiring.
- **`ERROR: failed to build … exit code: 255` inside a generated wrapper Dockerfile** – the base image publishes no build for this host's architecture, so the first `RUN` cannot execute. It reads as a broken build step but nothing from that image can run at all. The failure now names the image and both architectures. Most vulhub images are amd64 only; on an arm64 CORE VM install emulation (`sudo apt-get install qemu-user-static binfmt-support`, which persists across reboots) or choose a vulnerability publishing a build for your architecture.
- **`[OSError] [Errno 7] Argument list too long`, or several unrelated commands failing at once with no output** – a single environment value has exceeded the kernel's per-string limit (`MAX_ARG_STRLEN`, 128 KiB), after which *every* `execve` from that environment fails. Because the command never runs it prints nothing, so the blame lands on whatever ran next. Large payloads travel as files instead; if you add one, route it through `scenarioforge.utils.env_payload.set_env_payload`. To check by hand: `max((len(k) + len(v), k) for k, v in os.environ.items())`.
- **`docker compose pull failed … rc=1` with no output** – the command produced nothing because it never ran. Since v0 the message names the compose file, the exact command, and says explicitly when the output was empty. A frequent cause was selecting the v1 `docker-compose` binary on a host that only has the v2 plugin; the resolver now falls back to v1 only when it is actually on `PATH`.
- **`failed to fetch anonymous token … lookup auth.docker.io: no such host`** – the CORE VM cannot reach a registry. A run whose images are all cached should not need one: preflight skips the pull when every pull-only image is present, and cleanup keeps any image carrying a repo digest, because restoring a pulled image requires the network while rebuilding a local one needs only cached layers. If this appears for an image you expect to be cached, check it is still present (`docker image inspect <ref>`) and see [Operating Modes](OPERATING_MODES.md#image-retention-and-offline-runs).
- **`Persistent image pins were NOT applied to this run`** – the pinned list exceeded the size that can safely be handed to the remote run, so it was dropped rather than risk breaking every command on the CORE VM. The run is unaffected; only pin protection is lost for it, so pinned images may be removed and pulled again next time. The warning lists ways to reduce the set. Reaching this needs roughly three thousand pinned images.
